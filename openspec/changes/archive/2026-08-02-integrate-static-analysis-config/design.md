## 背景と制約

現状は `config` 配下に静的解析用 XML が存在しても、Gradle 側で SpotBugs/Checkstyle 実行タスクが十分に統合されておらず、VS Code 側とも参照整合が分離している。変更動機は proposal.md を参照し、本設計では「同一設定をビルドとエディタで再利用する方法」と「既存 XML の不整合修正方針」を定義する。制約として、既存の Java/Spring Boot/Gradle 構成を維持し、既存開発フローへの影響を最小化する。

## 目標 / 非目標

**目標:**
- Gradle の静的解析タスクが `config/checkstyle` と `config/spotbugs` を明示参照する。
- VS Code で表示される Checkstyle 診断と Gradle 実行結果のルール差分をなくす。
- `config` 配下 XML の誤り（無効パス、現在のパッケージ構成と不整合な抑制条件）を修正し、意図しない誤抑制を防止する。
- 開発者がローカルで再現可能な解析手順を README に明記する。

**非目標:**
- Java コード本体の機能追加や API 契約変更。
- 解析ツールの大規模なルールポリシー再設計。
- CI プラットフォーム固有のパイプライン実装変更。

## 設計上の意思決定

1. Gradle は専用プラグインで解析設定を固定化する。
- 採用: `checkstyle` と `com.github.spotbugs` を Gradle に導入し、設定ファイルパスを `config` 配下へ集約する。
- 理由: 開発者ごとの差異を減らし、ビルドコマンドで再現可能な解析結果を得るため。
- 代替案: VS Code 拡張のみで運用する方法は CI/CLI 再現性が不足するため不採用。

2. VS Code は既存設定を維持しつつ不足項目のみ補完する。
- 採用: `.vscode/settings.json` で Checkstyle 設定参照を維持し、必要に応じて Java 解析拡張向け設定を追加する。
- 理由: 既存開発体験を壊さずに設定差分を最小化できるため。
- 代替案: ワークスペース設定を全面置換する方法は他開発設定との競合リスクが高く不採用。

3. `config` 配下 XML は現在のソース構成に合わせて抑制条件を修正する。
- 採用: `suppressions.xml` の古いパッケージ参照を現行構成へ更新し、SpotBugs フィルタの不備があれば同時修正する。
- 理由: 無効な除外条件はノイズや誤抑制を生み、品質評価を不安定化させるため。
- 代替案: 一旦全抑制を削除する方法は警告増加で移行コストが高く不採用。

4. 実行導線を README に統一する。
- 採用: `./gradlew check` または個別タスク実行手順を明記し、結果出力先を固定化する。
- 理由: 新規参加者でも同じ手順で検証できるため。
- 代替案: 口頭運用のみは再現性を担保できないため不採用。

## リスク / トレードオフ

- [リスク] 新しい静的解析設定により既存コードで警告が増える可能性 → [緩和策] まず設定整合を優先し、必要最小限の抑制調整を段階的に適用する。
- [リスク] VS Code 拡張バージョン差異で表示結果が揺れる可能性 → [緩和策] Gradle 実行結果を基準とし、README で基準コマンドを明示する。
- [トレードオフ] 厳密化により初回 `check` 実行時間が増える可能性 → [緩和策] 開発中は個別タスクを許容し、PR 前に統合実行する運用にする。

## 移行計画

1. `build.gradle` に静的解析プラグインと設定参照を追加する。
2. `.vscode/settings.json` の静的解析参照先を確認し、必要な補完設定を追記する。
3. `config/checkstyle/suppressions.xml` と `config/spotbugs/exclude-filter.xml` の不整合を修正する。
4. `./gradlew check`（または解析タスク）を実行し、設定反映を検証する。
5. README に解析手順と出力確認方法を追記する。
