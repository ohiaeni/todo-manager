## コンテキスト

現状の実装はタスク一覧取得とユーザー登録が主であり、タスクの書き込み系操作は未定義である。動機は proposal.md を参照し、本設計では `task-management-api` と `todo-listing-api` の仕様差分を満たすための実装方針に限定する。技術制約は Java / Spring Boot / Gradle、既存の層構造（presentation / application / domain / persistence）を維持する。

## 目標 / 非目標

**目標:**
- ユーザーに紐づくタスクの登録・更新・削除 API を追加する。
- 一覧取得をユーザー境界でフィルタし、他ユーザーのタスクが混在しない契約に合わせる。
- 他ユーザー所有タスクに対する更新・削除を明確に拒否する。
- 既存テスト方針に合わせ、正常系とアクセス拒否系を自動テストで担保する。

**非目標:**
- 認証基盤そのもの（ログイン機能、トークン発行方式）の新規導入。
- 大規模な DB 正規化変更やマルチテナント戦略の再設計。
- 既存 API のバージョニング方針変更。

## 設計判断

1. ユーザー境界はアプリケーション層で一元判定する
理由: プレゼンテーション層の分岐重複を避け、更新・削除・取得で同一ポリシーを適用できるため。
代替案: コントローラーごとに所有者チェックを記述する案は、漏れや不整合が起きやすく採用しない。

2. 永続化アクセスは「タスク ID + ユーザー ID」を基本キーとして扱う
理由: 他ユーザータスクへの誤更新を SQL レベルでも防ぎやすく、要件の安全側に寄せられるため。
代替案: 先にタスク ID 単体で取得し後段で所有者比較する案は、チェック漏れ時のリスクが高い。

3. 一覧取得 API は「認証済みユーザーに紐づくタスクのみ返す」仕様へ更新する
理由: `todo-listing-api` の変更要件に直接対応し、フロントエンドの表示安全性を高めるため。
代替案: 既存の全件 API を残しクライアントで絞り込む案は、情報露出リスクがあるため採用しない。

4. エラー応答は「対象なし」と「権限なし」を明確に分離する
理由: クライアントのリカバリー分岐と監査ログ観点で、失敗理由の判別可能性が必要なため。
代替案: すべて 404/400 に統一する案は運用診断性を下げるため採用しない。

## リスク / トレードオフ

- [リスク] 既存データにユーザー紐づけ欠損があると、新仕様で取得漏れが発生する
  → 緩和策: マイグレーション前に欠損検出クエリを実行し、暫定補正データを投入する。

- [リスク] 所有者判定の実装箇所が分散すると、API ごとに挙動差が生まれる
  → 緩和策: アプリケーション層の共通サービス化と、拒否系テストの共通化を行う。

- [トレードオフ] ユーザー ID 条件追加でクエリが複雑化し、わずかな性能低下があり得る
  → 緩和策: インデックス確認と、必要に応じて `(user_id, task_id)` の複合キー最適化を行う。

## 移行計画

1. スキーマと永続化マッパーに、タスクとユーザー紐づけの前提を反映する。
2. アプリケーション層に登録・更新・削除ユースケースと所有者判定を追加する。
3. コントローラーに新規エンドポイントを追加し、入力検証とエラー変換を実装する。
4. 一覧取得処理をユーザー境界前提に置き換える。
5. 単体テスト・統合テストを追加し、既存テストを更新する。
6. ロールバック時は新規エンドポイントを無効化し、一覧取得の旧ロジックへ戻せるよう差分を分離してデプロイする。

## 未解決事項

- 認証済みユーザー ID をどの経路（ヘッダー、セッション、セキュリティコンテキスト）で受け渡すかは、既存実装の最終確認後に確定する。
- 更新 API の部分更新（PATCH）と全量更新（PUT）のどちらを標準とするかは、クライアント利用要件を確認して確定する。
