## 背景と制約

現状の実装とテスト構成は、追加されたテスト戦略インストラクションに対する責務分離と検証粒度が十分に揃っていない。変更の動機と対象範囲は proposal.md を参照し、本設計では実装整合の進め方を定義する。制約として、既存 API の外部契約は維持しつつ、Java / Spring Boot / Gradle の既存構成内で改善を行う。

## 目標 / 非目標

**目標:**
- 層ごとの責務に対応するテスト配置と命名を整理し、テスト戦略に準拠した構成へ統一する。
- 既存コードの振る舞いを保ったまま、テストしづらい結合点を解消し、ユニットテストと統合テストの境界を明確化する。
- ローカル環境で再現可能なテスト実行条件（設定、データ、起動手順）を標準化する。

**非目標:**
- 新機能の追加や API 契約の変更。
- 本変更と無関係な大規模リファクタリング。
- 本番運用監視の仕組み変更。

## 設計上の意思決定

1. テスト責務を層単位で明確化する。
- 採用: プレゼンテーション層は Web レイヤ中心、アプリケーション層はユースケース中心、インフラ層は永続化連携中心の検証を行う。
- 理由: 失敗時の原因特定を容易にし、テスト戦略の説明可能性を高めるため。
- 代替案: すべてを統合テストへ寄せる方法は実行時間増加とデバッグ難度の観点で不採用。

2. 既存実装の結合点をテスト容易性優先で調整する。
- 採用: 依存注入境界を活かし、モック可能な単位でアプリケーションサービスの振る舞いを検証する。
- 理由: API 契約を変えずに、既存コード修正の安全性を高められるため。
- 代替案: 大規模な責務再分割は影響範囲が大きいため今回は不採用。

3. テスト実行環境を設定ファイルとシードデータで標準化する。
- 採用: 既存のテスト用プロパティ・データ初期化資産を基準に不足分を補完する。
- 理由: 開発者ごとの差異を抑え、再現性のある失敗検知を可能にするため。
- 代替案: 外部コンテナ依存の複雑な実行基盤導入は準備コストが高いため不採用。

## リスク / トレードオフ

- [リスク] 既存テストの整理過程で一時的にカバレッジが低下する可能性 → [緩和策] 変更を小さな単位で分割し、各ステップで回帰確認を行う。
- [リスク] 実装調整が想定以上に広がる可能性 → [緩和策] API 契約不変更をガードレールにし、影響範囲を層ごとに限定して進める。
- [トレードオフ] テスト厳密化により初期の実行時間が増える可能性 → [緩和策] テスト種別の責務分担を明確にし、重複ケースを整理する。

## 移行計画

1. 既存テストを棚卸しし、テスト戦略に対する不足観点を層別に特定する。
2. 実装の結合点を最小限修正し、ユニットテストを先に整備する。
3. 必要な統合テストと実行環境設定を追加し、ローカルでの再現手順を固定化する。
4. 回帰確認後、変更内容をドキュメント化して開発フローに組み込む。
